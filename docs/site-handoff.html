Authoring blocks

A page is a document. Headings, paragraphs, lists and images outside tables are default content. A designed component is a block table: its merged first row names the block, and the following rows contain its content. Use the exact names and structures in the 32-block catalog.

Example structure: one complete Cards Article row per card

Optional eyebrow

Heading 3: Article title

Supporting copy, including any inline link.

Standalone link: Read the article

Another image

Heading 3: Another article

Supporting copy.

Standalone link: Read more

“Heading 3” and “Standalone link” above are instructions for formatting the cell, not text to paste into it. Insert the real image, choose the heading level, and create a real link in its own paragraph.

Rules that apply across the site

  • Keep the block name exact. Cards Article loads cards-article; Tabs Accounts is plural. Use parentheses for options, such as Hero Dark (Split, Balanced).
  • Copy a known example. Start with a reviewed page or a registered library example. Optional rows and extra cells vary by block; use its catalog entry rather than assuming every table has the same contract.
  • Keep actions separate. A standalone linked paragraph can become an action. An inline link stays in its sentence. Keep the original destination, campaign query parameters and disclosure markers.
  • Use one page H1. Use H2 for sections and H3 for cards or questions as appropriate. Do not select heading levels just to change size.
  • Choose suitable images. Follow the image preparation and crop guidance. Supply meaningful alternative text for informative images and empty alternative text for decorative artwork. Campaign artwork and logos must suit the selected surface.
  • Separate sections with a section break. A horizontal rule separates the document into sections. Section Metadata configures one section; Metadata configures the whole page.

Adobe explains editing in Layout, Content and Split views and the underlying sections, blocks and block options. Use this project’s catalog for the exact E*TRADE table structures and supported variants.

What a template change can affect

A starter document is copied content: future edits to the starter do not update its copies. A Fragment is shared content: changing its source affects consuming pages. A code change affects every page that uses that block or helper. The page-layout helper recognizes six existing routes, including Home, Welcome Back, Our Accounts, Brokerage, Planning and Why E*TRADE; duplicating one to a different address does not automatically carry its route-specific layout classes.

For a new page type, ask a developer to confirm its layout behavior at the new path. Do not invent Template values or new block names to imitate an existing layout.

What wins when options overlap

  1. Header Theme metadata overrides an explicit Header Light/Dark variant, which overrides a legacy page light/dark choice, which overrides the family’s header default.
  2. A section Theme selects a local family. A section Color Scheme independently selects light/dark text and the default background.
  3. An explicit block layout or surface, such as Columns Feature (Dark) or Accordion FAQ (Flat), keeps its documented behavior. Theme changes do not replace artwork.

Try the design system

Extending the system

Developers maintain palette and semantic roles in styles/brand.css, family overrides in styles/themes.css, section composition in styles/sections.css, and component layouts in their owning block stylesheets. Shared action and card rules live in styles/actions.css and styles/cards.css. Text and spacing use scalable values; narrow block containers and enlarged text reduce internal column counts.

Before rollout, set the intended family in DA, review both logo schemes in the shared nav, and review footer artwork and campaign images. The saved regression fixtures are examples, not evidence of the current DA metadata. Home should opt into Charcoal and Welcome Back into Purple; confirm the intended family for other imported pages.

Before inserting an asset

  • Use the approved source asset at enough resolution for its intended display; avoid enlarging a small thumbnail. Reuse established SVG logos/icons where available and suitable raster artwork for photographs.
  • Keep essential words, rates and legal terms as authored text. Do not rely on an image that is cropped, decorative or hidden on phones to communicate them.
  • Write alternative text for the information an image adds. A linked image needs an accessible link name; a decorative image beside equivalent copy can use empty alternative text.
  • Insert the actual image in DA. Preserve meaningful alternative text when replacing it; the previous image’s description may no longer be correct.

Check the result: preview on phone and desktop, check the crop and surrounding text, enlarge text to 200%, and follow any image link with the keyboard. The final rendered crop is the acceptance check.

09 / Authoring

Making an edit

  1. Open the correct page in DA. For demo-only behavior, use ?ref=demo before the URL’s #.
  2. Locate the block table and make the wording, image or link change. Preserve its heading row, row roles, tracking markers, disclosure IDs and any Rate settings cells.
  3. Save and preview the page. Review the rendered page at its .aem.page address on the intended code branch.
  4. Check phone and desktop layout, heading order, image alternatives, keyboard access, destination URLs and legal references.
  5. Publish through the normal content-release process, then verify the published page and shared dependencies.

For a campaign change, treat the headline, amount, deadline, promo code, calculator tiers, rate source, CTA destinations and corresponding legal copy as one content update. A screenshot or saved example is not the approval source for current offer terms.

If a change appears only in the editor, check the save and preview steps, the path and the code branch. A code merge does not publish edited DA content.

For reviewing an edit, see Adobe’s version comparison and restore workflow. Compare the selected version with the current page before restoring: restoration replaces current source content. Then review the restored result and follow the preview/publish workflow for the intended release.

Create a new page

Use this checklist for a new page; the shorter workflow above is for changing an existing one. Treat a copied page as a starting point whose inherited settings must be reviewed.

  1. Confirm the destination. Agree the final local path and content owner. Check whether it already exists; use an agreed draft path for experiments. A draft path alone is not an access restriction.
  2. Select a reviewed starting page. Choose the closest page pattern. Copy its native content into the new document without replacing an existing page. Record which content is local and which is shared.
  3. Choose the blocks. Use the selection guide and exact catalog names. Preserve complete rows and required row roles; remove sample copy and unused content deliberately.
  4. Set page metadata. Review Title, Description, Image, Theme, Disclosures and any Nav/Footer overrides. Remove copied campaign or service settings that do not apply; use the metadata reference.
  5. Prepare copy and assets. Supply approved wording, heading levels, images and alternatives. Review amounts, eligibility, dates, promo codes and action destinations together, including campaign query parameters.
  6. Resolve dependencies. Confirm that shared fragments, disclosure sets and every referenced legal fragment exist. Check target pages and use a separate Rate settings cell for each configured binding.
  7. Save, then preview. Use the intended code branch; remember that ?ref=demo changes rendering code rather than creating a content sandbox. Preview dependencies as well as the page.
  8. Review the rendered page. Check phone/desktop layout, 200% text, heading order, image crops, keyboard controls, final link destinations, rate/data state and the complete disclosure region. Review the delivered title, description and social image.
  9. Prepare the route into the page. Review navigation, footer, campaign and other incoming links. For a replacement or renamed path, agree the old-path/redirect handling with the site owner before changing links.
  10. Release and verify. Obtain the content approvals required for the page, deploy any prerequisite code, publish shared dependencies and target pages, then publish consuming pages/navigation. Open the live-delivery path and follow the real incoming links.

Done means: the intended published URL is reachable through its real entry links, shows the approved content and metadata, and loads the correct shared and legal sources. A saved draft or working demo preview alone does not meet that check.

Preview & publish

Single-page release

  1. Save the page and required shared sources in DA.
  2. In Experience Workspace, open Send, select Preview and choose Update. Review the resulting preview URL using the required code branch.
  3. Verify phone/desktop rendering, keyboard interaction, headings, images, destinations, rate state and the complete legal footer.
  4. When the content is ready for release and the required code is deployed, use Preview & Publish and Update. Verify the live-delivery page.

Preview updates the preview instance; Preview & Publish updates both preview and published content. The AEM Sidekick also exposes actions on rendered pages according to permissions and page state. See Adobe’s publishing guide for the current UI.

Adobe also documents Preflight for automated checks before release. Where available, review its findings alongside the manual page, data and legal checks above; this guide does not establish this tenant’s Preflight configuration.

Dependency and code checks

  • Preview/publish shared fragments and disclosure sets/fragments, not just the page referencing them.
  • Check that the code branch contains the blocks, options and metadata behavior used by the page. Content is shared across branches; unpublished content and undeployed code are independent.
  • For a code pull request, include a branch preview link such as https://{branch}--etrade--adobedrago.aem.page/home. A local screenshot does not replace branch review.
  • Check the published result after release. A working demo preview does not establish that main or the public E*TRADE domain has the same code/content.

Taking a page down

Use the editor’s Prepare → Unpublish flow when removal is intended. It removes preview and published delivery. Review incoming navigation links and any redirect requirement with the site owner before removing a page from an active journey.
